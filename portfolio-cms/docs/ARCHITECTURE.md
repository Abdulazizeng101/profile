# Architecture

A single Next.js application serves both the public portfolio and the private
dashboard. There are no separate services: one app, one PostgreSQL database and
one file store.

```
Browser ──► Next.js (App Router, React Server Components)
              ├── /en, /ar ............ public site (prerendered, cached, tag-invalidated)
              ├── /admin .............. dashboard (rendered per request, session required)
              ├── /api/admin/* ........ upload, export, preview (session + same-origin)
              ├── /cv ................. stable link → current CV file
              └── /media/* ............ files, local storage driver only
                       │
                       ├── PostgreSQL (Drizzle ORM) ── content, settings, sessions, rate limits
                       └── Storage driver ─────────── local disk  or  S3-compatible bucket (R2)
```

## Source layout

| Path                     | What lives there                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `src/app/[locale]/`      | Public pages. `[locale]` is the root segment (`en` / `ar`) so `<html lang dir>` is correct for each language.      |
| `src/app/admin/`         | Dashboard. `login/` is public; everything in `(dashboard)/` requires a session.                                    |
| `src/app/api/admin/`     | Route handlers for uploads, the JSON export and opening preview mode.                                              |
| `src/components/public/` | Public site components (server components unless marked `"use client"`).                                           |
| `src/components/admin/`  | Dashboard building blocks: forms, uploaders, sortable lists, Markdown editor.                                      |
| `src/components/ui/`     | Small accessible primitives (button, fields, switch, dialog) on Radix UI.                                          |
| `src/lib/`               | Code shared by server and browser: validation schemas (Zod), i18n dictionaries, date formatting, types.            |
| `src/server/db/`         | Drizzle schema and the database client.                                                                            |
| `src/server/auth/`       | Password hashing, sessions, `requireAdmin()` / `authorizeAdmin()`.                                                 |
| `src/server/actions/`    | Server Actions. Every admin action starts with `authorizeAdmin()`.                                                 |
| `src/server/admin/`      | Dashboard data access. Every function checks the session itself.                                                   |
| `src/server/content/`    | Cached public reads, localisation fallback, cache tags.                                                            |
| `src/server/media/`      | Upload validation, image processing (sharp), media usage tracking.                                                 |
| `src/server/storage/`    | Storage drivers behind one interface.                                                                              |
| `src/server/security/`   | Rate limiting, request helpers (client IP, same-origin), crypto helpers.                                           |
| `drizzle/`               | SQL migrations, generated by drizzle-kit and committed.                                                            |
| `scripts/`               | CLI: migrate, seed, create admin, reset password, export/import content (with files), `pg_dump` backup/restore.    |
| `tests/`                 | Vitest unit tests (`unit/`), Postgres integration tests (`integration/`) and Playwright end-to-end tests (`e2e/`). |

## Data model

24 tables, all with UUID keys (singletons use id `1`), timestamps, and
`sort_order` / `status` (draft | published) where content is repeatable.

```
admin_users ─< sessions                     rate_limits (login, contact, uploads)

profile ─< profile_translations             site_settings ─< site_settings_translations
  │ photo / cv_en / cv_ar ─────────┐          │ og_image ───────────────┐
                                   ▼                                    ▼
                               media_assets (metadata only; bytes in storage)
                                   ▲              ▲               ▲
project_categories ─< projects ─< project_images  │               │
                         │  └──< project_translations             │
                         └──< project_skills >── skills >── skill_categories
experiences ─< experience_translations, experience_skills >── skills
education ─< education_translations          (logo ─► media_assets)
accomplishments ─< accomplishment_translations (document ─► media_assets)
social_links       contact_messages
```

**Localisation rule.** Long-form content has a `*_translations` table keyed by
`(parent_id, locale)`. Short labels (category names, captions, alt text) use
paired `…_en` / `…_ar` columns. Language-neutral data (dates, URLs, order,
flags) lives on the parent row once.

**Fallbacks.** When Arabic text is missing, the public site either shows the
English text marked with `lang="en" dir="ltr"`, or hides the item, depending on
Settings › Languages. Nothing is machine-translated.

**One table for certifications, courses, awards, competitions, publications and
volunteer work** (`accomplishments.kind`), because they share every field.

**Experience status** (`planned | current | completed`) is validated against
the dates on every save and publish; planned roles render in a separate
"Upcoming" block.

## Rendering and caching

Cache Components is enabled (`cacheComponents: true`).

- Public reads in `src/server/content/public.ts` use `"use cache"` with
  `cacheLife("days")` and are tagged (`projects`, `profile`, …, plus `content`).
- Every admin mutation calls `updateTag()` for the tags it affects, so the next
  visitor sees fresh content immediately. No redeploy is involved.
- Public pages are prerendered at build time (`generateStaticParams` for both
  locales and every published project); new project pages render on first
  visit and are then cached.
- **Unpublished and unknown project URLs** show the site's 404 page, with a
  `noindex` tag, and never any of the project's content. Because pages stream,
  a production response may already have committed to status 200 by the time
  the page decides the project doesn't exist; Next.js cannot change it then
  (see "The HTTP contract" in the Next.js streaming guide). Search engines
  follow the `noindex`. A strict 404 status would need `ensureStatic =
'navigation'`, which rules out draft preview, or a database lookup in the
  proxy on every request, which defeats caching.
- **Preview** uses Next.js Draft Mode: `/api/admin/preview` (session required)
  sets the bypass cookie, and the public reads include drafts while it's on.
  Signing out disables it.
- The dashboard renders per request (`instant = false`); `loading.tsx` shows a
  skeleton while each page loads.

## Security model

| Concern       | Measure                                                                                                                                                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Passwords     | Argon2id (19 MiB, t=2, p=1). Minimum 12 characters. Constant-time path for unknown emails.                                                                                                                                             |
| Sessions      | 256-bit random token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie (`__Host-` prefix in production). Only its SHA-256 is stored. 7-day sliding expiry, 30-day absolute limit. Password change signs out other devices.             |
| Authorization | `authorizeAdmin()` at the top of every Server Action and admin route handler; `requireAdmin()` in every admin data function (works even when layouts aren't re-rendered on client navigation). The proxy redirect is only a fast path. |
| CSRF          | SameSite cookies + Next.js' Server Action origin check + an explicit same-origin check in `authorizeAdmin()` and the upload route.                                                                                                     |
| Brute force   | Postgres-backed rate limits: 20 login attempts / 15 min per IP, 5 failures / 15 min per email.                                                                                                                                         |
| Uploads       | Real type detected from bytes (JPG/PNG/WebP/PDF only), size limit, decompression-bomb limit, images re-encoded (strips EXIF/GPS), PDFs with scripts rejected, random server-generated keys, strict key pattern on read.                |
| Contact form  | Server-side Zod validation, honeypot, signed minimum-fill-time token, rate limit per IP (5/h) and global (60/h), optional Cloudflare Turnstile. IPs stored only as keyed hashes.                                                       |
| Output        | Markdown rendered without raw HTML; React escaping; JSON-LD escaped.                                                                                                                                                                   |
| Headers       | CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS in production; `noindex` and `no-store` on `/admin`.                                                                                            |
| Secrets       | Environment variables only; `.env*` ignored by Git; nothing secret is `NEXT_PUBLIC_`.                                                                                                                                                  |
| Errors        | Visitors see generic messages; details go to server logs.                                                                                                                                                                              |

The CSP allows `'unsafe-inline'` for scripts because nonce-based CSP would force
every page to render dynamically (no prerendering). User content can't inject
scripts because Markdown is rendered without HTML.

## Backups

`EXPORT_TABLES` in `src/server/db/export-tables.ts` is the single list of
content tables, shared by the dashboard export and the `content:export` /
`content:import` scripts. A unit test fails if a new table is added to the
schema without being added there (or explicitly excluded, like sessions). The
import replaces all content in one transaction. See [BACKUP.md](BACKUP.md).

## Why Drizzle instead of Prisma

The original brief preferred Prisma. Prisma's CLI downloads its migration
engine from `binaries.prisma.sh` at runtime, which the build environment for
this project could not reach, so migrations could not be generated or tested.
Drizzle is pure TypeScript, its migrations are plain SQL files in `drizzle/`,
and nothing is downloaded at deploy time. Queries are fully typed from the
schema, and the generated SQL is easy to review.
